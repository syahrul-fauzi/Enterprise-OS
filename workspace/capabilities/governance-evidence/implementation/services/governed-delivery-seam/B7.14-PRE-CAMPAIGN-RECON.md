## 🔍 Detailed Target Justification: ILC + evidence-registry

### G1: Business need (✓ TERPERINTAH)
ILC sudah memiliki pekerjaan bisnis nyata yang tercatat di `runtime-invocations.jsonl`:
```json
{"capability_id":"governance-evidence","operation_id":"get-audit-report",...}  // Sudah generate audit reports
{"capability_id":"workflow-engine","operation_id":"execute-plan",...}         // Sudah menjalankan workflow kompleks
{"capability_id":"security-hardening","operation_id":"authorize",...}        // Sudah mengelola akses
```
`evidence-registry` **dibutuhkan** untuk menyimpan, mengindeks, dan mengambil kembali audit reports yang sudah mereka generate.

### G2: Capability fit (✓ SEMANTICALLY TEPAT)
`evidence-registry` purpose: *"Central registry for storing, indexing, and retrieving all governance and runtime evidence across EOS."*  
ILC adalah produsen evidence (audit reports) yang membutuhkan registry ini. Fit sempurna tanpa paksaan.

### G3: Adoption contract (✓ BISA DIDEKLARASIKAN)
Cukup tambahkan 1 line di `products/ilc/product.binding.yaml`:
```yaml
capabilities:
  - requirement-management
  - evidence-registry  # ← Hanya ini yang perlu ditambahkan
```
Tidak ada custom coupling.

### G4: Canonical execution (✓ RUNTIME SUDAH SIAP)
ILC sudah memanggil capability cross-domain sebelumnya. Canonical runtime sudah mendukung:
```
ILC → governance-evidence (SUDAH BEKERJA)
ILC → evidence-registry (BISA LANGSUNG)
```

### G5: Governance continuity (✓ TIDAK PERLU SEAM BARU)
Tidak membutuhkan governed operation baru. existing workflow sudah memadai.

### G6: Evidence (✓ AKAN DIHASILKAN SECARA ALAMI)
- `production_usage` evidence akan terkumpul dari pemanggilan `storeEvidence()`
- `full_traceability` akan terpenuhi karena audit reports tersimpan di registry
- Artifacts yang dihasilkan adalah artifacts bisnis nyata, bukan buatan.

### G7: No architectural fork (✓ TIDAK PERLU ADAPTER)
Tidak perlu membuat adapter khusus, semantic fork, atau duplicate capability. Semua menggunakan existing canonical interfaces.

## 🚨 Critical Finding: ILC Sudah Memanggil Capability yang Tidak Terdaftar
**Di product.binding.yaml ILC hanya terdaftar:**
```yaml
capabilities:
  - requirement-management
```

**Tapi di runtime-invocations.jsonl ILC memanggil:**
- `workflow-engine`
- `governance-evidence`
- `security-hardening`

Ini adalah **bottleneck yang persis ingin kita buktikan**: capability sudah dieksekusi, tapi tidak terikat secara canonical di product.binding. Adoption process belum berjalan dengan deterministik.
